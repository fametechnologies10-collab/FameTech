# AT-iShare Console (SPFastIT) — Developer API Reference

**Source:** supplier-provided integration docs, captured 2026-08-21.
**Base URL:** `https://console.spfastit.com/api/`
**Network coverage:** AirtelTigo (AT-iShare) data bundles only.
**Transport:** `POST` with `application/x-www-form-urlencoded` body params (NOT JSON, NOT header auth).

> ⚠️ **This is NOT `lib/at-ishare-service.ts`.** That existing file is the **CodeCraft**
> wholesaler integration, which happens to also fulfill AT-iShare-network orders. The
> AT-iShare Console described here is a separate, standalone supplier (SPFastIT) where we
> hold our own MB balance and push transfers to beneficiaries. Keep the two clearly
> distinct in naming and in review.

---

## Authentication

Every request must include your valid `api_key`. Your account must also be active before
your API key can work.

> **Important:** API requests are deducted from your console balance when successfully
> queued or processed according to your system rules.

## Endpoint 1 — Send Bundle Request

`POST https://console.spfastit.com/api/send.php`

Use this endpoint to send a new AirtelTigo bundle request. The request is added to the
queue and processed automatically.

**Backward compatible duplicate protection.** Existing integrations may continue sending
only `api_key`, `phone`, and `bundle_mb`. New integrations should also send a stable
optional `client_reference` so the same request can be retried safely after a timeout.

### POST parameters

| Parameter | Required | Description |
|---|---|---|
| `api_key` | Yes | Your SPFastIT API key. |
| `phone` | Yes | Recipient number. Example: `0261234567` or `233261234567`. |
| `bundle_mb` | Yes | Bundle size in MB. Example: `1000` for 1GB. Your system uses **1000MB = 1GB**. |
| `client_reference` | No | A unique reference generated by your system, such as `ORDER-184250`. Maximum 100 characters. Allowed characters: letters, numbers, dot, underscore, colon, and hyphen. Reusing the same reference with the same phone and bundle returns the existing transaction instead of creating a duplicate. |

### Recommended cURL example

```bash
curl -X POST https://console.spfastit.com/api/send.php \
  -d "api_key=<API_KEY>" \
  -d "phone=0261234567" \
  -d "bundle_mb=1000" \
  -d "client_reference=ORDER-184250"
```

### Legacy-compatible cURL example

```bash
curl -X POST https://console.spfastit.com/api/send.php \
  -d "api_key=<API_KEY>" \
  -d "phone=0261234567" \
  -d "bundle_mb=1000"
```

### New transaction response

```json
{
  "status": "success",
  "message": "1000MB request queued successfully.",
  "queue_status": "queued",
  "transaction_id": "EXTQ_123_20260721214530_A1B2C3D4",
  "duplicate": false,
  "phone": "233261234567",
  "bundle_mb": 1000,
  "client_reference": "ORDER-184250"
}
```

### Existing transaction recovery response

```json
{
  "status": "success",
  "message": "Existing transaction returned. No new queue request was created.",
  "queue_status": "queued",
  "transaction_id": "EXTQ_123_20260721214530_A1B2C3D4",
  "client_reference": "ORDER-184250",
  "duplicate": true,
  "phone": "233261234567",
  "bundle_mb": 1000,
  "created_at": "2026-07-21 21:45:30"
}
```

### Reference conflict response

```json
{
  "status": "error",
  "message": "This client_reference has already been used for a different phone number or bundle size.",
  "client_reference": "ORDER-184250"
}
```

### Error response

```json
{
  "status": "error",
  "message": "Invalid API key or user not active."
}
```

## Endpoint 2 — Check Order Status

`POST https://console.spfastit.com/api/check_order_status.php`

Use this endpoint to check a transaction using the `transaction_id` returned for either a
newly queued request or an existing transaction recovered with `client_reference`.

### POST parameters

| Parameter | Required | Description |
|---|---|---|
| `api_key` | Yes | Your SPFastIT API key. |
| `transaction_id` | Yes | The transaction ID returned after sending a bundle request. |

### Possible statuses

| Status | Meaning |
|---|---|
| `queued` | Waiting to be processed. |
| `processing` | Currently being processed. |
| `pending_retry` | Provider timed out. System will retry. |
| `completed` | Transaction completed successfully. |
| `failed` | Transaction failed. |
| `failed_blocked` | Number is blocked from receiving data. |
| `billed_failure` | Provider returned a billed failure response. |

### cURL example

```bash
curl -X POST https://console.spfastit.com/api/check_order_status.php \
  -d "api_key=<API_KEY>" \
  -d "transaction_id=EXTQ_123_20260628123456_123456"
```

### Queued response example

```json
{
  "status": "success",
  "message": "Transaction is queued and waiting to be processed.",
```

`POST https://console.spfastit.com/api/check_balance.php`

Use this endpoint to check your wallet balance, reserved queue balance, and available
balance.

### POST parameters

| Parameter | Required | Description |
|---|---|---|

## Recommended Integration Flow (supplier's own guidance)

1. **Create a stable client reference.** Generate one unique reference for your local
   order, for example `ORDER-184250`. Keep the same reference for every retry of that
   order.
2. **Send the bundle request once.** Call `/api/send.php` with `api_key`, `phone`,
   `bundle_mb`, and the optional `client_reference`.
3. **Save the transaction ID.** Store the returned `transaction_id` in your own system. A
   response with `duplicate: true` is a successful recovery of the existing request, not a
   new queue entry.
4. **Recover safely after a timeout.** If the send response is lost, retry the exact same
   phone, bundle, and `client_reference`. The API returns the existing transaction instead
   of creating another request.
5. **Check status until final.** Call `/api/check_order_status.php` with the saved
   `transaction_id`. Continue checking while the status is `queued`, `processing`, or
   `pending_retry`.
6. **Update your local order.** Only treat `completed` as final success. Handle `failed`,
   `failed_blocked`, and `billed_failure` according to your own billing and review rules.

---

## Important Notes (supplier's own)

- The system uses **1000MB = 1GB**.
- `client_reference` is optional, so existing integrations remain compatible.
- Use a unique client reference for each local order and never reuse it for a different
  phone or bundle size.
- Retrying the same reference with the same phone and bundle returns the existing
  transaction without creating a duplicate.
- Always save the returned `transaction_id` and use it to check order status.
- Queued, processing, and pending retry requests may **reserve** part of your wallet
  balance.
- **Do not treat queue acceptance as completed delivery. Only `completed` is final
  success.**
- If your API key is exposed, regenerate it from your Profile page.

# ── Integration analysis — OUR notes, NOT from the supplier docs ──

Everything below this line is KiNG FLEXY GH analysis written 2026-08-21 while reading the
docs above. It is not supplier-stated behaviour. Treat every "unverified" item as something
to confirm against the **live endpoint** before enabling this supplier in production — per
`kingflexy-fulfillment` checklist items 9 and 16, a spec is not evidence.

## What this API gives us that others don't

- **A real client-supplied idempotency key on placement** (`client_reference`), and — unlike
  DataKazina — resending it is a *successful recovery* (`duplicate: true`), not an HTTP 422
  rejection. This is the single best property of this API: a dropped connection is fully
  recoverable by replaying the identical request.
- Consequence: this supplier should **NOT** need the `ambiguous: true` failure mode that
  HendyLinks and AgentPortal require (checklist item 7). Recovery is deterministic.
- **No bundle mapping is needed at all.** Unlike DataKazina (numeric package IDs resolved via
  `fetchAllBundleMappings()`) and Bundle Portal, this API takes a **raw MB integer**. The
  entire mapping is `bundle_mb = GB × 1000`. There is no catalogue to fetch, no cache layer,
  and no `admin_settings` bundle-map row. The console is an MB wallet drawn down per send.

## What this API lacks

- **No webhook.** Delivery status is poll-only, exactly like Bundle Portal. Needs a
  `sync-atishare-console-status` cron sweep (model on
  `app/api/cron/sync-bundleportal-status/route.ts`).
- **No transaction list / history endpoint.** There is no way to sweep "all my recent
  transactions" — status lookup is by `transaction_id` only. So `transaction_id` MUST be
  persisted immediately after dispatch or the order is only recoverable by replaying its
  `client_reference` through `send.php`. (Checklist item 18: write the supplier id to the
  DB straight after dispatch, never at the end of a bulk run.)
- **No documented rate limits.** Non-blocking — use a conservative dispatch concurrency
  (Bundle Portal uses 5) until observed otherwise.

## Traps identified in these docs

1. **Balance is denominated in DATA (MB/GB), not currency.** Every other supplier's
   `fetchSupplierBalance()` in this repo returns `{ balance, currency: 'GHS' }` and the
   admin UI renders it as money. `available_mb` / `available_gb` will render as
   "GHS 95" if fed through the existing contract unchanged. This needs an explicit
   decision, not a silent cast.
2. **`available_mb` is the number that matters, not `wallet_balance_mb`.** Queued and
   processing requests *reserve* balance (`reserved_queue_mb`). A pre-flight balance check
   against `wallet_balance_mb` would over-report headroom and let us queue orders the
   console cannot actually satisfy.
3. **Errors appear to come back as HTTP 200 with `status: "error"` in the body.** No HTTP
   status codes are documented anywhere in these docs. `response.ok` is therefore
   **not** a usable success signal — parse `body.status`. (Unverified; confirm against live.)
4. **`billed_failure` is a money-affecting terminal state and must never be auto-retried.**
   "Provider returned a billed failure response" means the upstream may have charged us
   while delivery failed. This is a manual-review state. Auto-retrying it risks paying
   twice for one undelivered bundle.
5. **`failed_blocked` is a business rejection** (recipient number blocked from receiving
   data). Per checklist item 9 it must (a) NOT call `recordFailure()` / trip the circuit
   breaker, and (b) be fallback-worthy. Getting this wrong is precisely what caused
   HendyLinks' supplier-wide self-inflicted outage on its first production day.
6. **Timestamps carry no timezone** — `"2026-07-21 21:45:30"`. Checklist item 17 applies
   verbatim: never `new Date(theirString)`; append `Z` explicitly and assert exact UTC
   equality in tests so they fail under any `TZ`.
7. **`client_reference` must vary per deliberate admin retry but NOT per cron re-dispatch.**
   Same shape as DataKazina's `buildIncomingApiRef` (checklist item 13): key the suffix on
   `orders.retry_count`, which is written ONLY by the `claim_order_retry` RPC. Reason: a
   failed transaction replayed under its original reference returns the *existing failed*
   transaction forever, so a retry would never actually re-submit. Conversely, keying the
   suffix on a timestamp or a cron-advanced counter would mint a brand-new **paid** console
   order on every cron pass.
8. **The reference-conflict error is NOT retryable.** If the same `client_reference` is
   ever sent with a different phone or bundle size, the request is permanently rejected.
   Our reference must therefore be derived from the order id (which pins phone + bundle),
   never from anything mutable.
9. **1000MB = 1GB, not 1024.** Bundle-size mapping must use decimal, or every size is
   silently off by 2.4%.
10. **Phone accepted as `0XXXXXXXXX` or `233XXXXXXXXX`, echoed back as `233XXXXXXXXX`.**
    Normalize on our side before comparing an echoed value to what we sent.
11. **API key travels in the POST body.** It must come from an env var
    (`ATISHARE_CONSOLE_API_KEY`), be added to `.env.example` when the service file is
    written (checklist item 15), and never be logged — body-logging a failed request would
    write the key into logs.

## Observations to confirm against the live endpoint

**None of these block implementation.** The documented `status: "success" | "error"` body
contract is enough to build against; these are things to note from the first real
responses, in the spirit of checklist item 16 (verify field names against the live
endpoint, and paste a verbatim response into the tests).

| # | Observation | Why note it |
|---|---|---|
| 1 | Exact body of an **insufficient balance** rejection | Should be classified as a business rejection (leave `pending` for a console top-up), not an instability failure that trips the breaker. Until seen, any `status: "error"` that is not a recognised transport fault is treated as a non-breaker-tripping rejection. |
| 2 | Whether errors ever use non-200 HTTP codes | We detect success from `body.status`, not `response.ok`, so either way works — worth confirming so the service file's comments stay truthful. |
| 3 | How long `pending_retry` persists, and the console's own attempt count | Informs the polling cadence and when a stuck transaction should be surfaced for manual review. |
| 4 | Whether a `failed` / `failed_blocked` transaction returns the reserved MB to our balance | Affects only how we read the balance display, not order handling. |
