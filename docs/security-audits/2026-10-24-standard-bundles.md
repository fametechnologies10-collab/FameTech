## Findings

| F1 | LOW (confidence: high) | `app/api/standard-bundles/purchase/route.ts:75-96`, migration `reference_code` UNIQUE (global, not per-user) | The client idempotency key maps to a globally-unique `reference_code`, but the pre-insert replay check is scoped `.eq('user_id', userId)`. If a second user's purchase attempt happens to collide on the same `reference_code` (same UUIDv4 idempotency key), the second insert fails the UNIQUE constraint, triggers a refund, and `replayOf()` (scoped to the *second* caller's `user_id`) returns null — so that caller gets a generic 500 "Failed to create order" instead of a replay, even though their wallet was correctly refunded. No money is lost or double-charged; it is a UX/DoS edge case only. | Collision requires guessing another user's random UUIDv4 idempotency key — computationally infeasible in practice (122 bits of entropy) — or an extraordinarily unlikely accidental collision. | Not worth fixing given the entropy; if hardened, could additionally key the replay lookup off `reference_code` alone first (global) before falling back to the per-user check, and return a clearer "try again with a new request" error instead of a bare 500. Documented here as a theoretical edge case only. |
| F2 | INFO | `lib/standard-bundles-fulfillment.ts:68-74`, `shouldAlertExhausted` | When dispatch retries are exhausted, the code explicitly does **not** auto-refund ("an earlier attempt may have delivered") and only alerts an admin. ## Verified safe (controls confirmed by direct code reading)

- **Webhook HMAC order of operations**: raw body read via `request.text()` and verified with `verifyKingFlexySignature` *before* `JSON.parse` — `app/api/webhooks/kingflexy-commission/route.ts:27-35`. Rejects with 401 before any DB access on bad signature.
- **Webhook payload gating**: `decideBundleWebhook` (`lib/standard-bundles-logic.ts:150-165`) requires `product === 'bundles'`, a non-empty string `reference`, and a mapped terminal state (`completed`/`failed`) — anything else is ignored with a 200, never processed.
- **Wallet credits only via RPC, never direct UPDATE** in application code: `refund_standard_bundle_wallet` RPC is the only path (`lib/standard-bundles-finalize.ts:59`, admin route `app/api/admin/standard-bundles/orders/route.ts:253`). The RPC itself (`supabase/migrations/20261024_standard_bundles.sql:97-102`) does the wallet UPDATE, but only inside the function, not from route code.
- **Row locked `FOR UPDATE` before the idempotency/status check**, exactly per the repo's documented race-fix convention: `SELECT * INTO v_o FROM ... WHERE id = p_order_id FOR UPDATE` (line 79) happens before the `status NOT IN (...)` check (line 85) and before the compare-and-set check (line 89). Verified this prevents double-credit: two concurrent calls on the same order serialize on the row lock; the loser sees the now-`refunded` status and returns `reason: 'not_refundable'`.
- **Compare-and-set on admin refund**: `p_expected_updated_at` passed from the order row read *before* the supplier verification round-trip (`app/api/admin/standard-bundles/orders/route.ts:256`, value captured at line 169-173, before the `checkBundleOrder` await at line 232) — a webhook/cron finalize landing in that window correctly aborts the admin refund with `reason: 'changed'` (line 262-264 in route; RPC line 89-91).
- **RLS / grants on `standard_bundle_orders`**: owner-only `SELECT` policy (`auth.uid() = user_id`), `INSERT/UPDATE/DELETE/TRUNCATE` revoked from `anon`/`authenticated`, plus the `block_client_money_writes()` guard trigger as defense-in-depth even if a grant were mistakenly re-added (migration lines 39-53). Matches the existing money-table pattern this repo already relies on.
- **RPC execute privilege**: `refund_standard_bundle_wallet` has `REVOKE ALL FROM PUBLIC, anon, authenticated` + `GRANT EXECUTE TO service_role` only (migration lines 119-120) — not callable by an authenticated user's browser client, only from server code using the service-role client.
- **Client price never trusted**: `app/api/standard-bundles/purchase/route.ts` takes no `price`/`total_paid` from the request body; `catalogPrice` always comes from the server-fetched catalog (`getBundleCatalog`, line 136) or, for broadband, a bounds-checked amount validated against the catalog's own `min`/`max` (`validateBroadbandAmount`, `lib/standard-bundles-logic.ts:240-249`). Confirmed in the dashboard client (`app/dashboard/standard-bundles/page.tsx`) that only `value`/`packId`/`amount` (bounded) are sent, never a price field.
- **Discount clamp defense-in-depth**: `parseDiscountSetting` clamps to `[0, 50]` at read time (`lib/standard-bundles-logic.ts:85-89`) independent of `validateBundleSettingsInput`'s own `[0,50]` validation on write (lines 345-358) — a bad value written by any other path still can't exceed 50% when charging.
- **Amount/price mismatch handling for standard bundles**: `resolveBundleForPurchase` fails closed (`ok: false`) if a catalog row's `amount` and `price` diverge by more than 0.005, or if a `pack_id`-bearing row is purchased as `'standard'` (`lib/standard-bundles-logic.ts:266-276`), and `findBundle` never falls back from a vanished `pack_id` to a `value` match (line 79-83 comment + logic) — prevents a Special Bundle disappearing from the catalog from silently resolving to an unrelated standard bundle.
- **Idempotency/replay scoping**: purchase-route replay lookup is scoped to both `reference_code` AND `user_id` (route.ts:78-83) before any debit; dispatch claim uses an atomic conditional UPDATE (`.eq('status','pending').eq('fulfillment_attempts', ...)`, `lib/standard-bundles-fulfillment.ts:81-88`) so only one worker (auto-dispatch `waitUntil` vs. cron Pass G vs. admin retry) can claim a given order for a KingFlexyGH call at a time.
- **No SSRF/injection on outbound KF calls**: base URL is a hardcoded constant (`KF_BASE_URL`); the only user-influenced path segment (`reference`) is `encodeURIComponent`-escaped (`lib/kingflexy-bundles-service.ts:253`); all other data goes in a JSON body via `fetch`, not string-concatenated into a URL.
- **No secret leakage**: `describeKfFailure` explicitly redacts the API key out of any error message before it's logged or could reach a response (`lib/kingflexy-commission-service.ts:212-215`, confirmed unchanged logic, only its export visibility changed in this branch).
- **No raw supplier text surfaced to customers**: customer-facing failure notification uses the constant `BUNDLE_FAILURE_CUSTOMER_MESSAGE` (`lib/standard-bundles-logic.ts:212`), never `outcome.reason` — verified in `lib/standard-bundles-finalize.ts:146,167`. Raw KF payloads (`kf_event.raw`) are stripped before reaching the admin orders list (`trimMetadata`, `app/api/admin/standard-bundles/orders/route.ts:39-51`), and the customer `history` route explicitly selects only customer-safe columns, excluding `fulfillment_metadata`, `kf_order_ref`, `commission_amount` (`app/api/standard-bundles/history/route.ts:13-19`).
- **PostgREST `.or()` search injection**: the admin orders search term is whitelist-filtered to `[A-Za-z0-9 _@.+-]` and length-capped at 40 before being interpolated into `.or(...)` (`app/api/admin/standard-bundles/orders/route.ts:97`), stripping the `,`/`(`/`)` characters that would otherwise let a caller inject additional OR conditions.
- **Admin authorization**: both admin routes call `validateAdminAccess(false)` as literally the first statement in every handler before any other work (`orders/route.ts:20-26,61-62,158-159`; `settings/route.ts:14-20,45-46,57-58`); sub-admins are explicitly excluded from the orders route (comment + `validateAdminAccess(false)`).
- **Cron auth ordering**: `validateCronAuth(request)` is the first line of the `GET` handler in `app/api/cron/kingflexy-commission-reconcile/route.ts:34-35`, no logic precedes it.
- **Rate limiting**: `/api/standard-bundles/purchase` has both a Redis-backed middleware limiter (5/min, keyed on `authUser.id + ip`, `middleware.ts:112,946-948`) and a fail-closed critical-path fallback limit if Redis is down (`middleware.ts` fallback table, 5/min) plus a per-instance in-route backstop (`consumeRateLimit`, 10/min, `purchase/route.ts:71-72`). Catalog fetches from KingFlexyGH are memoized in-memory + persisted to `admin_settings` with a 15-minute TTL (`isCatalogFresh`/`CATALOG_TTL_MS`) and single-flight de-duplicated (`inflight` map, `lib/kingflexy-bundles-service.ts:185-195`), so neither the customer `catalog` route nor repeated admin catalog-preview calls can amplify into repeated live supplier calls.
- **Late "completed" after refund never reverses the refund**: confirmed in `finalizeBundle`'s completed branch (`lib/standard-bundles-finalize.ts:108-120`) — a 0-row guarded update (meaning the order already left `processing`/`pending`) triggers an admin alert explicitly when the order is `refunded`/`failed`, with no code path that re-credits KingFlexyGH or reverses `standard_bundle_orders.status` back from `refunded`.
- **Regression check on existing airtime/utility webhook & cron logic**: the `lib/kingflexy-commission-service.ts` diff is export-visibility-only (`class KfBreaker` → `export class KfBreaker`, etc.) — confirmed via the diff hunk, no behavioral change. The webhook route's airtime/utility branches (lines 76-131) are unmodified in control flow; the bundles branch is inserted as an early return (lines 38-74) before the existing `decideKfWebhookAction` path, so it cannot alter airtime/utility dispatch.
